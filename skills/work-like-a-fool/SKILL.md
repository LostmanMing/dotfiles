# 定制化教程生成

> "Stay hungry, stay foolish." —— 求知若饥，虚心若愚。（乔布斯 2005 斯坦福演讲，引自《全球概览》）
> 所以这个 skill 的第一步不是教，而是先让学习者看清自己不懂什么——虚心若愚，然后才有得学。

## Overview

把「我要完成 X 但基础不够」变成两样东西：一份摸清知识边界的测评，和一套按测评结果裁剪、
在用户真实环境里验证过的教程站点。核心价值不在于知识本身（模型都会），而在于
**按实际缺口裁剪** + **在目标机器上真跑过**。

## 工作流程

两个阶段，**中间必须停下来等用户答题**。

```
阶段一（本次会话）              用户答题            阶段二（用户贴回结果后）
────────────────────           ─────────          ──────────────────────────
① 澄清任务与已有基础     →                    →   ⑤ 读测评结果，做诊断
② 探测真实环境                                    ⑥ 规划章节（按缺口裁剪）
③ 拆知识维度、出 20+ 题                           ⑦ 边写边跑，记录真实输出
④ 建站 + 起服务 + 给访问方式                      ⑧ 画图、校验、交付
```

## 阶段一

### ① 澄清任务与基础

用户的初始描述通常不够。**凡是需要用户拍板的选择（任务分叉、交付形态、优先方向、
是否安装某依赖等），一律用 `AskUserQuestion` 工具让用户选**，不要替他假设、也不要用纯文本追问。
**最多问 1–2 轮**，然后就动手。

必须搞清（问不到就在测评的 CONTEXT 里问）：
- 任务的**具体形态**（要交付什么：一次性分析 / 可复用工具 / 提交给上游 / 只是读懂）
- 目标场景的**关键分叉**（任务往往有几条走向不同的路径，选哪条会决定一半的课程内容）
  ——这类分叉值得单独问
- 可投入时间

不要问「你了解 X 吗」——那是测评要回答的，问了反而浪费轮次。

**贯穿全流程的两条工具规则：**
- **需要用户回答/决策时 → `AskUserQuestion`**（阶段一的澄清、阶段二的方向确认等）。
- **总结知识面 / 拆维度 / 出题 / 规划章节时 → 先用 `WebSearch` 核实**（见 ③）。

### ② 探测真实环境（不要跳过）

```bash
python3 <SKILL_DIR>/scripts/probe_env.py
python3 <SKILL_DIR>/scripts/probe_env.py --python /path/to/venv/bin/python
```

若关键依赖缺失且值得装，**在后台装**（`run_in_background`），同时继续出题。装之前先测
网速选镜像，装完立刻验证可用性。详见 `references/grounding.md`。

### ③ 拆维度、出题

**先用 `WebSearch` 核实知识面，再动笔。** 不要只凭模型记忆总结「完成这个任务需要哪些知识」——
记忆会过期、会有盲区，尤其涉及具体框架/工具/库时。至少在以下节点搜索：
- 拆知识维度前：搜任务领域的现状、主流方案、关键概念，确认维度划分没有遗漏或过时。
- 出到涉及具体接口/版本/最佳实践的题时：搜官方文档/权威来源核对事实，避免把错的写进解析。
- 用当前年份作为搜索关键词的一部分，优先取最新信息；把可信来源记下来，供阶段二写课程时复用。

然后从任务反推 4–7 个知识维度，再出 20–26 道题。
**完整方法论见 `references/quiz-design.md`，出题前必读。**

题目数据写进 `<site>/assets/questions.js`，契约：

```js
const TOPIC = { title: "标题", goal: "一句话说清最终目标" };
const CATS = { key1: { name: "维度名" }, /* 4-7 个 */ };
const QUESTIONS = [
  { cat: "key1", level: 2, multi: false,
    text: "题干（可含行内 HTML）", opts: ["A", "B", "C", "D"],
    answer: [1], why: "解析：为什么 + <b>这一点对完成任务的具体影响</b>" },
];
const SELF = [["key", "自评项标签"]];                      // 0-5 滑块，比选择题覆盖更宽
const CONTEXT = [{ id: "x", label: "问题？", placeholder: "例：..." }];  // 3-5 项自由填写
```

要点（易错）：
- `answer` 是**索引数组**，单选也要写成 `[1]`
- 每个维度 ≥ 2 道；难度 ★:★★:★★★ ≈ 3:5:2；多选占 15–25%
- 安排 2–3 道题，其答案**直接就是任务的关键技术选型**——答错正好在开篇纠正
- `why` 写「对任务的影响」，不写教科书定义

### ④ 建站并交付访问方式

```bash
python3 <SKILL_DIR>/scripts/scaffold.py --dir <site> --title "..." \
        --subtitle "..." --chain "技术链路图（纯文本）" --quiz-only
# 写 <site>/assets/questions.js（覆盖占位文件）
python3 <SKILL_DIR>/scripts/validate.py --dir <site>
python3 <SKILL_DIR>/scripts/serve.py --dir <site>
```

`serve.py` 会自动检测是否 SSH 环境并打印对应的访问方式（端口转发 / 直连 / scp 拷回）。
把它的输出转述给用户，**并说明「答完点复制结果发回给我」**。

然后**停下来**。不要预先生成课程页——那违背整个方法的目的。

## 阶段二（用户贴回测评结果后）

### ⑤ 诊断

对照三样东西：选择题分项、自评滑块、CONTEXT 的回答。

- **自评高但答错** → 有盲区，或术语对不上；开篇要先统一术语
- **自评低但答对** → 有直觉不自信，可以讲快
- **留空的题** → 知道自己不知道，是明确的空白区
- **CONTEXT 的回答** → 常常改写一半的课程规划，优先级最高

产出一张诊断表放首页：维度 / 测评状态 / **课程策略（跳过什么、重点讲什么）**。
再用 `<div class="key">` 说清「你缺的不是 X，而是 Y」。

### ⑥ 规划章节

- 一节「错题精讲」放最前面：把答错的题背后的事实逐个讲透，10 分钟能读完。
  这是完成率最高、性价比最高的一节。
- 主线 6–10 节，按依赖排序，把最关键的 2–3 节标为「骨干」。
- 最后一节是「落地」：架构建议 + 分周路线图 + 验收标准（几个「必须能回答的问题」）。
- 扎实的维度**明确写「跳过」**；空白的维度从零讲。
- 规划前**用 `WebSearch` 核对**该领域的最新最佳实践与学习路径，确认章节顺序与取舍没过时。
- 若章节走向存在多个合理方案且影响较大，用 `AskUserQuestion` 让用户选，不要自己拍。

```bash
python3 <SKILL_DIR>/scripts/scaffold.py --dir <site> --title "..." --modules modules.json
```

`modules.json`：`[{"file":"m01.html","nav":"M1 全景图","mod":"M1","title":"全景图","goal":"读完能做什么"}]`
（scaffold 不会覆盖已存在的页面，可反复运行以更新导航）

### ⑦ 写内容：边写边跑

**每节都要有真跑过的东西。** 这是本 skill 的核心要求，见 `references/grounding.md`：

- 所有 API 签名去真实头文件/运行时核对，不凭记忆
- 每个动手环节先自己执行，把**真实输出**贴进 `<div class="real">`
- 调试中踩到的坑（尤其静默失败）写成课程内容——现象 → 根因 → 解决 → 教训
- 真实数字若推翻了你的预设，那正是最有价值的内容，要突出写
- 可跑的脚本放 `<site>/labs/`，并写一份 `labs/README.md` 附实测结果备份

### ⑧ 画图与校验

单页结构、样式类、SVG 规范见 `references/lesson-design.md`。
**分层、调用链、数据结构、算法机制这四类内容必须配图**，手写 SVG 存 `assets/img/`。

```bash
python3 <SKILL_DIR>/scripts/validate.py --dir <site>   # 必须 PASS 才算完成
```

校验覆盖：题目数据契约、答案索引越界、页面/资源引用、残留占位符、SVG 合法性、导航完整性。
